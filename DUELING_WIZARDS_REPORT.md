# Frontier duel: product-changing local OMP evaluation

Research date: 2026-09-29. Scope: choose which local model plus memory/side-work configuration is reliable and useful for actual OMP jobs on **this** Mac, under localbench's existing one-resident-model, loopback, MUST-conformance, ≤10-second cold tool-turn and current-incumbent comparison rules. This is an idea and implementation-plan study, **not** a measured profile verdict. The study did not launch a controlled localbench inference/training run, attack, external benchmark reproduction, profile switch or golden regeneration. Existing OMP sessions and their local-memory sidecars may still have used the GPU; no host-wide absence of local inference was measured.

## Promotion contract for the new duel

Both models received the same corrected primary-source pack after independently surveying separate ecosystems, then generated 30 new candidates each without reading the other's slate. Each independently scores the other's original five finalists on buyer value, novelty against the 61-Bead graph and 62 exclusions, causal falsifiability, source validity, local fit, and maintenance cost. Cross-scores are **design judgments, not independent runtime verification**. A finalist with no new user/operator action, an unenforced test-only flag, or a duplicate `lb-08`/memory-oracle acceptance rule is demoted regardless of score. Existing gates and privacy constraints are unchanged.

**Operator-slate challenge:** pane 2's [adversarial product-fit review](runs/frontier-duel/PRODUCT_FIT_CHALLENGE_PANE2_LUNA.md) found **no unconditional winner**. Project-locked environments have no demonstrated link to the named OMP latency/memory problem; LoRA lacks a named behavior, dataset and serving path; offline packaging lacks an operator need. Its subsequent [recipe nonduplication audit](runs/frontier-duel/MODEL_RECIPE_NON_DUPLICATION_PANE2_LUNA.md) rejects a new recipe Bead: `localbench create` already builds named Safetensors derivatives, Ollama supports broader Modelfiles, and the **historical OMP 18.2.11 full-request fixture** records 73,779 prompt tokens without an evidenced recipe-setting remedy. That fixture is not a fresh OMP 18.4.3 measurement. A recipe remains a *future conditional* only after a concrete user task/failure and missing directive are established; no model action now. A separate [Pi source/gateway review](runs/frontier-duel/PI_GATEWAY_FEASIBILITY_PANE3_LUNA.md) demotes first-class Pi ownership: Pi documents compatible endpoints and isolated CLI sessions, but the current localbench gateway registry is rebuilt from **OMP profiles**; forwarding Pi through one misattributes traffic. A disposable, uniquely attributed Pi trial is conditional on Pi becoming an explicit target; OMP-only mission/goldens cannot be relabeled as Pi results.

OMP's pinned [`memory_edit` fact-row guard](https://github.com/can1357/oh-my-pi/blob/fc671eba383f2a7208500836673b485c0dc7073d/packages/coding-agent/src/mnemopi/state.ts#L337-L385) and [`memory` working-row save with requested asynchronous fact extraction](https://github.com/can1357/oh-my-pi/blob/fc671eba383f2a7208500836673b485c0dc7073d/packages/coding-agent/src/mnemopi/backend.ts#L292-L320) expose a separate, potentially product-moving question: **can the user select and revoke one explicitly user-saved, project-scoped source and its proven descendants, then observe their absence from future recall without removing unrelated banks?** An extracted fact has a distinct ID and an approved-procedure provenance contract has not been established. The [same-model adversarial source challenge](runs/frontier-duel/MEMORY_REVOKE_CHALLENGE_LUNA.md) established a narrow gap, corrected here against [Mnemopi's pinned store implementation](https://github.com/can1357/oh-my-pi/blob/fc671eba383f2a7208500836673b485c0dc7073d/packages/mnemopi/src/core/beam/store.ts#L191-L221): a fact row cannot be edited directly through OMP's `memory_edit` (a later eligible bank with a colliding ID may still be edited); `forget` takes a **working-row** ID and can cascade deletion of its linked extracted facts; `invalidate` retires working or episodic rows, not facts; broad backend clear removes scoped database paths; and `localbench memory --prune` removes harness-owned banks only. A saved working-row ID is not proof that asynchronous extraction created a fact-row ID. None is a user-authorized operation selecting one explicit-save source and preserving other records and banks. This establishes a missing **inspected API path**, not an approved user workflow, data ownership, privacy guarantee, need, or implementation seam. The existing G73 oracle can check memory outcomes but does not grant user authorization over a source; a new benchmark-only row would duplicate G73. Do not bypass OMP's fact protection with SQLite edits or call broad clear a revoke.

Pane 3's follow-on [source-only feasibility audit](runs/frontier-duel/MEMORY_CONTROL_FEASIBILITY_LUNA.md) tightened the candidate. OMP's explicit user `memory save` creates a **source** row whose extracted facts have different IDs; agent-callable `memory_edit` has `approval = "read"` and an ID-only target, not user approval plus an exact project selector. The standalone Mnemopi CLI/MCP mutate working rows but use their own bank/session resolution and no OMP project authorization. Core `forgetWorking` does delete linked source facts/projections transactionally, but the inspected cascade omits graph `triples`; asynchronous extraction can write a visible orphan after deletion unless a source-existence fence is serialized with the delete. These are pinned-source risk paths, **not** reproduced attacks or proof that an actual user's data remains retrievable. A localbench wrapper must not call low-level CLI/MCP/SQLite mutators or claim that a confirmation prompt invoked by an agent proves user approval.
Primary anchors: [OMP agent `memory_edit` approval and schema](https://github.com/can1357/oh-my-pi/blob/fc671eba383f2a7208500836673b485c0dc7073d/packages/coding-agent/src/tools/memory-edit.ts#L12-L35), [source-delete transaction](https://github.com/can1357/oh-my-pi/blob/fc671eba383f2a7208500836673b485c0dc7073d/packages/mnemopi/src/core/beam/store.ts#L804-L818), [cascade](https://github.com/can1357/oh-my-pi/blob/fc671eba383f2a7208500836673b485c0dc7073d/packages/mnemopi/src/core/beam/store.ts#L172-L219), [triple writer](https://github.com/can1357/oh-my-pi/blob/fc671eba383f2a7208500836673b485c0dc7073d/packages/mnemopi/src/core/beam/consolidate.ts#L308-L321), and [asynchronous fact extraction](https://github.com/can1357/oh-my-pi/blob/fc671eba383f2a7208500836673b485c0dc7073d/packages/mnemopi/src/core/beam/store.ts#L306-L346).

**Product precedent, not OMP proof:** the dated, read-only [vendor API comparison](runs/frontier-duel/MEMORY_COMPETITOR_PRODUCTS_LUNA.md) found [Mem0 per-record update/delete](https://docs.mem0.ai/core-concepts/memory-operations/delete), [Zep episode/edge/node graph deletion with shared provenance retained](https://help.getzep.com/deleting-data-from-the-graph), and [Letta per-agent archival-passage deletion](https://docs.letta.com/api/python/resources/agents/subresources/passages/methods/delete). These are live documentation pages, not immutable source revisions or exercised accounts. They establish real operator products but not a safe OMP project resolver, user approval or complete deletion here; [Zep explicitly delegates consequential-action confirmation to applications](https://help.getzep.com/v3/memory-security). Candidate KEEP for distinct user action; direct localbench/MCP/SQLite mutation DROP. No competitor result upgrades the existing mission or justifies accessing the user's memory.

**Decision:** retain the user-owned memory-control action as an **UNPROVEN product candidate**, not a shipped feature or benchmark gate. A localbench implementation Bead becomes actionable only after OMP/Mnemopi supplies a supported **user-only** operation with exact project/bank and source/derived-record identity; that upstream operation must enforce transactional cascade, extraction-writer fencing and authorization independent of agent tools. The implementation Bead would require (1) an isolated known-good approved source revoke with future-recall **and** store-state absence, (2) known-bad agent-initiated, wrong-bank, same-ID collision, extraction-race and stale-ID refusals, (3) preservation of unrelated rows/banks, and (4) an alternative-valid decision to leave the item intact. An absence-of-recall probe alone cannot prove deletion. Until the upstream contract exists and those proofs are run, do not claim a usable revocation feature, modify user memory, or treat source review as a Mac runtime test.
